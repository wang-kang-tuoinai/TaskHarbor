# 操作契约：Claim

> 适用于当前 Go 异步任务平台初版，与其余六份操作契约配套使用。初版仅 Redis，不引入 MySQL。
>
> 任务详情为 Redis Hash，租约仅记录在 lease ZSET 的 score；不设置取消标记，不保存 execution_deadline_at 或详情中的 lease_expires_at。

## 1. 操作目的

执行实例从自己订阅的逻辑队列中领取一个任务，为本次执行尝试取得执行权。

Claim 成功表示平台已原子授予执行权，不表示 handler 已经开始执行。

响应可能丢失，因此恢复不能依赖执行实例一定接收到任务。

## 2. 调用方与输入

### 调用方

执行实例中的领取模块。

领取前先取得一个本地执行槽。在途 Claim 与尚未退出的 handler 都占用执行槽。

### 参数与配置

| 项目 | 来源 | 约束 |
| --- | --- | --- |
| `owner_id` | 执行实例启动时生成，随领取请求传入 | 非空，实例间唯一，重启后使用新的实例 ID |
| 订阅队列及权重 | 执行实例配置 | 至少订阅一个合法逻辑队列，不从未订阅的队列领取 |
| 租约时长、续租间隔 | 平台运行配置 | 均为正值，续租间隔小于租约时长并留出网络余量 |
| `attempt_token` | 平台领取模块生成，原子绑定到候选任务 | 每轮成功授予执行权使用新的唯一值，不由业务提交方指定 |
| `execution_timeout_ms` | 读取任务在 Submit 时保存的配置 | 单次执行时长上限，不能在 Claim 时擅自覆盖 |

attempt_token 可以在调用存储脚本前生成，再由脚本绑定到实际选中的任务，不要求 Lua 自己生成 UUID。

attempt_token 不是领取请求去重 ID。

业务调用方不在 Submit 时指定 owner_id、attempt_token、租约时长或续租间隔。

Claim 调用方不指定目标 task_id，任务由平台从可领取队列中选择。

多队列选择遵循执行实例的队列配置，权重选择算法不在本契约内展开。

## 3. 执行前置条件

### 本地领取条件

- 实例尚未停止接收新任务。
- 已取得一个空闲执行槽。
- 没有执行槽时，不向存储发起 Claim。

这里限制的是任务执行并发数，不是进程中的 goroutine 总数。

### 存储中的候选任务条件

- 候选 ID 属于所选队列的 pending 索引。
- 任务记录存在。
- status = pending。
- attempts < max_retry + 1。
- 不应残留当前执行身份、active 成员或租约索引。

发现记录缺失、状态冲突等情况，按一致性异常处理，不将其交给 handler。

所有条件检查与授予执行权必须在同一个原子边界内完成，不能先在存储外检查，再单独修改。

重试任务也经由 pending 被领取。

pending 表示当前可领取，不仅指第一次执行。

## 4. 成功后的变化与返回值

### 状态与数据变化

状态变化只有：

```text
pending → running
```

active 是执行中索引，lease 是租约到期索引，它们都不是任务状态。

在同一原子边界内完成：

1. 检查候选任务的状态、索引、执行身份与尝试额度。
2. 从 pending 移除该 task_id。
3. 将 task_id 加入 active。
4. 设置 status = running。
5. 写入 owner_id 和新的 attempt_token。
6. 将 attempts 恰好增加一。
7. 设置 last_claimed_at。
8. 建立初始租约并写入 lease 索引。
9. 如保存 updated_at，则同步更新。

时间戳统一为 Unix 毫秒，execution_timeout_ms、retry_delay_ms 为整数毫秒：

```text
lease ZSET 的 member = task_id
lease ZSET 的 score = Redis 当前时间（毫秒）+ 租约时长（毫秒）
```

last_claimed_at 和租约时间均在 Lua 中使用 Redis TIME 生成。lease ZSET 是租约到期时间的唯一来源，不将 score 重复写入任务详情。

初始租约不按 execution_timeout_ms 截断；单次执行超时由 Server 本地定时器控制，不由 Redis 保存或强制执行固定截止时间。

Claim 不修改原始提交配置，不清空最近一次失败历史。

授予执行权即消耗一次尝试。即使 handler 未启动或 Claim 响应丢失，也不退回该次数。

回收操作本身不再次增加 attempts。

### 返回值

| 结果 | 返回内容 | 本地后续动作 |
| --- | --- | --- |
| 成功领取 | 任务内容、本轮执行身份及 execution_timeout_ms | 登记到本地任务管理，启动 handler 时同时建立完整时长的本地超时定时器，并启动续租，执行槽转交任务执行流程 |
| 暂无可领取任务 | 明确的空结果，例如 task=nil、error=nil | 释放执行槽，等待后续轮询 |
| 参数、存储或一致性错误 | 可识别错误，不返回可执行任务 | 不启动 handler，释放本轮执行槽，按错误类型处理 |

成功结果至少包含：

- task_id。
- task_type。
- payload。
- queue。
- attempts。
- owner_id。
- attempt_token。
- execution_timeout_ms。
- last_claimed_at。

读取任务内容可以包含在原子操作中，但网络响应送达不属于存储原子保证。

Server 从成功响应取得 execution_timeout_ms，完成本地登记后，在启动 handler 协程的同时建立时长为 execution_timeout_ms 的本地定时器及取消 context。计时从启动 handler 开始，不从 Claim 请求发出、Redis 授予执行权或响应到达时提前开始。

Claim 请求、响应及 handler 启动前的准备耗时不计入 execution_timeout_ms，不需要统计领取耗时或从执行时长中扣除。没有启动 handler 时，不存在本轮执行定时器已经耗尽的判断；若最终不启动 handler，可归还原领取槽，已授予的执行权仍按租约和尝试预算恢复。

超时裁定与 handler 成功返回之间，本地只能选择一个结果处理分支。裁定超时后，停止续租、发出 context 取消并调用 ReportFailure，不再发起该轮 complete。上报未成功时，Redis 状态可能延迟到租约到期才由 Reclaim 推进。

续租和上报在 Lua 内仍必须检查当前状态、token 以及 lease score，不能复活过期租约。

第一版不在本地维护租约有效期，也不实现迟到 Claim 响应的租约到期判断。成功响应可能对应已失效的租约，handler 仍可能启动；后续 Renew、complete、ReportFailure 会由 Redis 检查并拒绝无效身份。该窗口以及本地租约到期保护属于待开发功能，不能描述为已解决。

## 5. 原子性与不变量

### 原子边界

以下检查与修改必须具有一致的原子边界：

- 候选任务检查。
- pending 移除。
- active 加入。
- 任务状态变化。
- 执行身份绑定。
- 尝试次数递增。
- 初始租约建立。

采用 Redis Lua 时，先校验输入、记录、数据类型与业务条件，再执行修改。

脚本隔离执行不等于运行时错误会自动回滚此前写入，实现不能依赖不存在的回滚能力。

脚本部分写入后的不完整状态不在正常执行保证内，自动检测、对账和修复不属于第一版。不能声称回收器能够恢复所有此类不一致。

如果未来使用 Redis Cluster，同一个原子脚本访问的相关 key 还需满足同槽要求。

### 不变量

- 同一任务不能同时位于 pending 和 active。
- active 中每个任务都有对应的 running 记录、当前执行身份和 lease 索引项。
- running 任务对应 active 和 lease。
- 租约可能已经过期但尚未被扫描回收，因此 running 本身不证明业务仍在推进。
- 同一任务最多只有一个当前有效执行身份。
- 当前有效身份唯一，不等于物理上绝无两个 handler 同时运行。
- 0 ≤ attempts ≤ max_retry + 1。
- 每次成功授予执行权，仅增加一次 attempts。
- 未收到响应的任务不会因缺少本地信息而失去恢复路径。
- execution_timeout_ms 是不可变配置，续租不重置本地执行定时器。
- 不保存 execution_deadline_at；Redis 不提供按执行时长拒绝迟到上报的硬截止保证。
- 终态统一为 completed、failed、canceled，终态任务不保留等待或执行索引及当前执行身份。

上述保证以权威存储可用且数据完整为边界。存储自身故障的持久性保证另行说明。

## 6. 失败及结果未知时的行为

### 参数错误

owner_id 为空、队列配置非法等情况，返回参数错误，不授予执行权。

### 前置条件不满足

- 没有执行槽：本地不发起领取。
- 没有任务：正常返回空结果。
- 候选任务记录缺失或状态不一致：返回或记录明确的一致性错误，不启动 handler。

初版不能静默丢弃异常候选 ID，也不能假定已经完成修复。

隔离和修复策略另行定义。

### 存储或网络异常

连接错误或超时可能发生在操作生效前，也可能发生在操作生效后。

不能根据错误直接推断任务仍然位于 pending。

### 响应丢失或结果未知

- 不猜测已经领取了哪个任务。
- 不启动 handler。
- 不为未知任务续租。
- 释放本轮本地执行槽。
- 后续可以按照轮询与退避策略发起新的 Claim。

新的 Claim 可能领取另一个任务，不能视为取回上一次结果。

已经生效但无人管理的领取，依靠租约到期回收兜底，不是依靠续租兜底。

存储客户端不得对结果未知的 Claim 启用未经审查的透明重试，否则一次本地领取可能在存储侧授予多个任务执行权。

## 7. 并发竞争规则

以权威存储中的原子生效顺序决定结果。

| 竞争关系 | 合法结果 |
| --- | --- |
| 多个实例领取同一任务 | 只有一个取得本轮执行权，其他调用只能取得别的任务、空结果或明确错误 |
| 取消先于 Claim 生效 | 等待任务进入 canceled 并移除等待索引，Claim 不得再授予执行权 |
| Claim 先于取消生效 | 先进入 running，Cancel 随后直接改为 canceled，移除 active、lease 并撤销当前身份；通知 Server 尽力停止 handler |
| 回收与新一轮 Claim 交错 | Reclaim 在同一 Lua 内选候选、读取当前状态和到期时间并迁移；旧轮次不得撤销新身份 |
| 旧执行者续租、上报与新一轮执行交错 | 当前 token 或有效期不匹配的操作被拒绝，不修改新一轮数据 |

Lua 是实现原子判定的一种方式，不能替代上述业务竞争规则。

已知取消衔接缺陷：Cancel 可能在 Claim 已生效、Server 尚未完成本地登记时推送通知，通知被忽略后 handler 仍可能启动。Redis 仍保持 canceled 并拒绝后续续租和上报，但无法撤销 handler 的业务副作用；第一版保留该缺陷，不承诺立即停止或绝不启动已取消任务。

续租、完成、失败和回收操作，也必须实现匹配的身份与状态检查。

## 8. 重复请求与幂等规则

- 初版普通 Claim 不提供请求幂等能力。
- 不保存 claim_request_id → 任务的映射。
- 相同 owner_id 发起两次调用，表示两次独立领取。
- 有足够任务时，两次调用可以领取两个不同任务。
- attempt_token 用于区分执行轮次，不用于找回上一次丢失的领取响应。
- 每次独立领取都受本地执行槽约束。
- 同一实例不能绕过并发限制反复领取。
- 请求去重保留期不适用。

若未来增加幂等 Claim，必须另行定义：

- 请求身份。
- 请求到任务的映射。
- 映射保留期。
- 租约失效后的重复请求返回规则。
- 迟到响应的处理方式。

## 9. 崩溃与恢复行为

| 故障时机 | 可能状态 | 恢复方式 |
| --- | --- | --- |
| 请求尚未生效，实例退出 | 任务仍在 pending | 其他实例正常领取 |
| 请求在途时实例退出 | 可能尚未领取，也可能已经授予执行权 | 未领取的继续等待，已领取且无人续租的到期回收 |
| 存储已经生效，响应丢失 | running、active、lease 已建立，本地不知道任务 | 回收器凭存储中的租约发现并处理 |
| 已接收任务，handler 启动前或执行中实例退出 | running，续租停止 | 租约到期回收 |
| handler 卡住但进程仍在线 | 本地超时前可能仍在续租 | 本地定时器触发后停止续租、取消 context 并 ReportFailure；上报失败则到期回收，执行槽仍等 handler 实际退出 |
| Redis 自身崩溃或故障切换 | 是否丢失近期变更取决于持久化与复制配置 | 按明确部署配置恢复并验证，不能仅凭 Lua 推导绝不丢数据 |

### 回收器的配套要求

初版使用 lease ZSET：

```text
member = task_id
score = 租约到期的 Unix 毫秒时间
```

active 与 lease 同时包含任务属于正常情况。

回收器在同一个 Lua 脚本中有界分批查找到期候选、检查当前条件并完成迁移，不将脚本外扫描结果作为直接修改依据。score 到期不会自动触发业务迁移。

脚本中的检查至少包括：

- 当前状态。
- 当前执行身份。
- 当前租约是否到期。
- 是否还有尝试额度。

与其余操作契约保持一致，回收后的去向为：

| 条件 | 目标状态 |
| --- | --- |
| running、租约已到期、尝试额度耗尽 | failed |
| running、租约已到期、还有尝试额度 | retry_wait |
| 已经 canceled 或其他终态 | 不再迁移或重试；正常 Cancel 已移除 lease，残留项按一致性异常处理 |

进入 retry_wait 时，读取任务 Hash 中不可变的 retry_delay_ms（默认 30 秒，最小 15 秒），计算 next_retry_at = Redis 当前时间（毫秒）+ retry_delay_ms，仅将该值写入 retry ZSET 的 score。next_retry_at 是重试到期时间的名称，不作为字段单独存入任务详情 Hash。

重试时间到达后，由 Reclaim 在 Lua 内原子移除 retry 成员、将状态修改为 pending 并加入 pending 一次。

回收时必须原子完成：

- 移除 active。
- 移除 lease。
- 撤销当前执行身份。
- 写入目标状态。
- 更新对应等待索引或终态信息。

不得重复入队，也不再次增加 attempts。

### 续租与本地执行限制

续租只针对本地明确接收并管理的具体任务和 attempt_token。

不能因为 owner 进程在线，就给其名下所有任务续租，否则响应丢失的任务可能一直无法回收。

超时或失去执行权后，执行端向 handler 发出取消信号。

明确失去执行权、已知取消、本地超时或完成/失败上报流程结束后，从续租集合移除该任务。complete、ReportFailure 对结果未知或存储/网络异常最多额外重试两次（含首次最多三次）；耗尽后停止续租，未完成的 Redis 状态由到期回收处理。停止续租和删除执行身份管理信息不能提前归还仍存活 handler 的执行槽。

Go context 不会强制终止 goroutine。本地执行槽应在 handler 真正退出后释放，不能一边遗留运行中的 handler，一边无限领取新任务。

attempt_token 保护平台状态，不能撤销邮件、扣款等外部副作用，业务仍需要幂等。

回收不承诺强制杀死旧 handler。

本地租约有效期维护及按租约到期主动停止 handler 是待开发功能，第一版不实现。Renew 网络异常或响应丢失时，等待下一次续租，不仅凭该次错误判定已经失去执行权；因此旧 handler 可能在 Redis 租约过期后继续执行，直到收到明确拒绝、本地超时或 handler 自行退出。

## 10. 验收场景

| 场景          | 操作                                 | 期望结果                                                       |
| ----------- | ---------------------------------- | ---------------------------------------------------------- |
| 正常领取        | 提交一个任务后领取                          | pending 移除，active 和 lease 建立，状态 running，身份完整，attempts 恰好加一 |
| 无空闲槽        | 占满本地执行槽后触发轮询                       | 不发送新的 Claim                                                |
| 空队列         | 对空订阅队列领取                           | 正常空结果，执行槽释放，无任务数据变化                                        |
| 非法实例参数      | 传入空 owner_id                       | 参数错误，不领取任务                                                 |
| 两实例竞争       | 同时领取唯一 pending 任务                  | 恰好一个获得本轮执行权                                                |
| 取消与领取竞争     | 分别安排取消先、领取先                        | 符合第 7 节两条取消竞争规则                                            |
| 两次普通 Claim  | 准备两个任务与两个空闲槽，连续调用                  | 获得两个不同任务，不把第二次当作幂等重试                                       |
| 领取响应丢失      | 实际完成领取，再由存储封装层丢弃结果并返回模拟超时          | 本地不执行、不续租，任务到期后可回收                                         |
| 已领取实例崩溃     | 领取成功后结束实例进程                        | 回收后按剩余额度进入 retry_wait 或 failed，无遗留孤立 active 项                  |
| 迟到上报        | 回收并重新领取后，用旧 token 续租或上报            | 明确拒绝，不修改新一轮状态、结果或租约                                        |
| 多回收器竞争     | 两实例同时触发同一队列 Reclaim，各自在 Lua 内选候选和迁移 | 同轮只迁移一次，不重复加入 retry 或 pending，不撤销新一轮身份                 |
| 本地超时        | handler 超过 execution_timeout_ms 且 Server 正常调度 | 本地裁定超时、停止续租并 ReportFailure，不重置定时器；Redis 状态可能延迟收敛       |
| 超时计时起点     | 人为增加 Claim 请求、响应和本地登记耗时，再启动 handler | 从启动 handler 时计满 execution_timeout_ms，不扣除领取或准备耗时                  |
| 超时上报失败     | 丢弃超时 ReportFailure 的请求或响应，耗尽重试 | 停止续租，到期回收；不假定 Redis 已经立即结束该轮                                  |
| 取消登记窗口     | Cancel 通知先于本地登记到达并被忽略 | 记录为已知缺陷：handler 可能启动，但 Redis 不接受后续续租和结果                   |
| 本地租约保护延期 | 模拟迟到 Claim 响应或持续续租网络错误 | 不把本地租约到期判断列为已实现；Redis 仍按状态、token、score 拒绝失效操作         |
| 不响应 context | handler 忽略取消并继续运行                  | 不声称已强制停止，本地执行槽直到实际退出才释放                                    |
| 不一致候选       | pending 中放入不存在记录的 ID               | 明确报错或告警，不执行、不静默吞掉异常                                        |

领取响应丢失与实例崩溃会消耗已经授予的尝试预算。

因此，本契约不承诺 handler 最终一定被调用，更不承诺业务副作用恰好发生一次。


第一版队列范围：Server 固定领取 default，任务 Hash 中 queue 必须为 default；不提供自定义队列或多队列调度。毫秒配置转换为本地 time.Duration 时须检查溢出。详见 [ADR-0001](adr/0001-submit-client-and-storage.md)。
