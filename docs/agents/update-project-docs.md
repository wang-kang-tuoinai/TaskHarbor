# 更新项目进度与概览

让读者快速了解项目是什么、目前做到哪里。更新后的文档应反映最新事实，并保持清晰的信息分工。

## 先建立依据

1. 确认当前项目根目录，阅读项目的 `AGENTS.md` / `agents.md` 和目标文档。默认查找 `docs/当前进度.md`、`docs/项目概览.md`；用户指定路径优先。路径不明确时先查找已有文件，存在多个候选时再询问。
2. 查看相关工作区改动和未跟踪文件，结合本次工作记录，按需读取相关代码、测试、操作契约、ADR 或实施计划。未提交不等于未实现；计划写完不等于代码完成；测试代码存在不等于实际运行通过。
3. 确定事实变化，再决定需要更新哪份文档。两份文档可以只改一份；没有相关变化时保持不变。

以已确认契约和 ADR 判断设计，以实际代码判断实现，以真实执行记录判断验证。发现来源冲突时说明冲突及影响，保留待确认状态，不自行更改设计以消除矛盾。

## 信息放在哪里

| 信息 | 主要归属 | 两份摘要文档的处理方式 |
| --- | --- | --- |
| 项目定位、目标与非目标、核心概念、整体架构、模块职责 | 项目概览 | 保留理解项目所需的稳定摘要 |
| 当前阶段、已完成能力、验证范围、阻碍、下一步 | 当前进度 | 按最新状态合并更新 |
| 接口输入输出、字段语义、默认值、上限、错误与重试细则 | 操作契约或已有接口文档 | 用一句能力描述和必要引用承接 |
| 决策背景、替代方案、取舍及替代关系 | ADR | 必要的架构结论融入概览已有章节，理由引用 ADR |
| 实施步骤、逐文件改动、详细测试场景和执行过程 | 已有实施计划、任务或验证记录 | 保留必要摘要及已有证据链接 |

先确认被引用材料确实存在且包含相应信息。不能用一个空链接替代唯一的事实或验证证据。没有详细记录可引用时，在进度中保留最小但足够的证据摘要；仅为缩短摘要，不另建报告或扩张文档体系。

## 项目概览：保持稳定的全局视角

- 说明项目解决的问题、范围、核心组件如何协作、关键业务流程和文档入口。
- 仅在定位、范围、架构、模块职责、关键流程或文档入口变化时修改。修正已有的过时事实也属于有效更新。
- 将必要的架构变化融入对应章节。目录说明保持组件或目录级职责，个别文件仅在帮助导航时列出。
- 参数表、字段细则、某次实施决策清单、测试命令、环境版本和阶段验收结果归入上表对应来源。完成一个模块时，不在概览末尾追加该模块的完成报告。
- 对尚在开发的项目，保留一处简短说明，区分目标架构与当前实现；具体模块完成状态统一引用当前进度。若依赖版本必须精确，引用现有配置或正式支持声明，避免维护可直接查得的版本副本。
- 保留理解系统所必需的设计边界，例如并发、执行权、业务幂等和持久化保证；压缩措辞不能改变这些语义。

## 当前进度：维护当前快照

沿用现有结构，合并同义章节；缺乏合适结构时按以下信息组织，不必机械创建所有标题：

- **当前阶段**：目前处于哪里，哪些能力已完成，主要尚缺什么。
- **已完成能力**：按模块或能力概括，一项通常一至两句；较早阶段逐步压缩，详细依据使用引用。
- **验证摘要**：记录必要的日期、验证范围、结果及影响结论的环境条件；命令或详细记录仅保留能帮助判断、定位和复现的部分。
- **当前限制与阻碍**：仍影响正确性、交付、运行或下一步的事项，以及关键未验证范围。
- **下一步**：当前优先任务、可判断完成的结果和真实前置条件；后续候选用短句概括。

更新规则：

- 用新状态替换过时状态，合并重复完成项；完成一个模块后收敛为能力摘要，而不是继续追加日期小节、决策回顾和逐文件清单。
- 已设计、已实现、已验证分别表述。局部通过不扩展为全流程完成；一次环境通过不扩展为兼容性或部署保证。
- 本次执行的测试和沿用的历史验证明确区分。保留历史验证的日期、范围和限制；相关代码变化后未复验时，说明当前验证缺口。
- 只为整理文档，无须启动服务或重跑整个测试集。缺少证据时如实标记未验证；确需重新验证且在任务授权范围内时再执行。
- 保留现有的启动批准、设计确认和其他真实前置条件；收到新的明确授权后同步状态。将“本轮不做”等会话措辞改成持续可理解的项目状态。
- 已解决阻碍在有依据时移除或改为结果摘要；重要未决问题和风险不能因精简而消失。

## 编辑与收敛

1. 在已有章节内更新、替换、合并，只有确有独立信息类别时才新增章节。不要求每次更新增加篇幅，也不以固定字数强行裁剪。
2. 每个详细规则保留一个权威来源，摘要仅复述理解全局或当前状态必需的结论。同一文档内相同完成情况只说明一次。
3. 删除或压缩前，检查该段是否含有其他地方尚未保留的事实、限制、证据或用户约束。保留其最小必要表达，或引用已核实的来源。
4. 保留现有用户改动，改动限于本次授权范围。整理两份摘要不附带修改代码、契约、ADR、实施计划或项目规则；需要扩展范围时另行说明。
5. 遵循用户已有的审阅要求：若要求先展示草案，则先给出具体改动再等待确认；已获批准的同一范围无需重复确认。

## 本项目常见归类示例

遇到概览中的“Submit 已接受决策”段落，分别判断：

- 固定单队列等结论，只有在界定项目范围或解释架构时才在对应章节简述；已经说明则合并重复内容。
- `max_retry` 默认值与数值上限、配置单位和 Hash 字段比较细则，由相关操作契约和 ADR 承接，不在概览维护参数副本。
- Submit 完成情况、本机 Redis 验证和兼容性待验证范围，合并到当前进度已有能力、验证或限制项中，不再追加一份 Submit 汇报。
- 已有 ADR 和实施计划的入口放到相关文档索引；确认来源覆盖信息后，再删除混合段落。

这个例子说明信息归类，不能作为当前实现和测试状态的依据。每次都按本次项目事实判断。

## 完成检查与反馈

检查改动后的文档和差异，确认：

- 概览能快速解释项目，进度能快速定位现状；完成报告没有再次混入概览。
- 重复、失效和已被新事实替代的内容已收敛；链接相对于所在文档有效，摘要与来源一致。
- 验证结论有依据，设计与实现有区分，重要风险和授权边界仍然清楚。
- 未借机增加新的文档体系，未覆盖无关改动。

简短报告更新了哪份文档、主要合并或删减了什么，以及仍缺少的证据或待确认事项。只改一份或无需修改时，说明原因即可。
