# 操作契约：Submit

> 适用于当前 Go 异步任务平台的初版设计。初版仅使用 Redis，不引入 MySQL；任务详情存储于 Hash，索引迁移通过 Redis Lua 完成。
>
> 七份契约统一使用 pending、running、retry_wait、completed、failed、canceled 六种状态，其中后三种为终态。不设置取消标记。

## 1. 操作目的

业务调用方向任务平台提交任务，使任务进入可被领取的等待状态，并使用自己提供的任务 ID 查询任务或安全重试。

Submit 成功表示平台已接受该任务，不表示任务已经执行成功，也不保证响应到达时任务仍处于 pending。

## 2. 调用方与输入

### 调用方

业务服务或其他 API 调用方。

初版不要求开发 Client SDK，普通 HTTP 调用方也可以接入。客户端自动重试由调用方自行决定，不属于当前平台的实现范围。

### 输入参数

| 字段                  | 含义                                   | 约束                                           |
| ------------------- | ------------------------------------ | -------------------------------------------- |
| `task_id`           | 整个任务的唯一标识                            | 必填、非空，由调用方提供，平台不自动生成；同一次逻辑提交的重试必须复用          |
| `task_type`         | 执行端查找 handler 使用的任务类型                | 必填、非空，符合平台规定的格式与长度                           |
| `payload`           | 交给 handler 的业务参数                     | 无参数任务允许为空，大小不能超过平台配置上限                       |
| `max_retry`         | 首次尝试之外允许重试的最大次数                      | 可选，默认 0，非负整数；0 表示不重试                              |
| `execution_timeout_ms` | 单次执行尝试的时长上限                          | 可选，单位为整数毫秒；省略时默认 60000；显式提供时必须大于 0，且不超过平台公开的时长上限 |
| `retry_delay_ms`       | 每次进入 retry_wait 后等待下一次可领取的时长 | 可选，单位为整数毫秒；省略时默认 30000；显式提供时必须 ≥ 15000，且不超过平台公开的上限 |

### 参数规范化

max_retry 省略时规范化为 0，与显式 0 等价；保存并比较最终值，并确保 max_retry + 1 可安全表示。

Go API 使用 time.Duration，允许整数毫秒输入，例如 1500ms；非整数毫秒必须拒绝，不得截断。payload 最大 1 MiB（1048576 字节），nil 与空切片统一为空字节，不要求 JSON。task_id 不自动裁剪或改写。

任务类型的具体格式与长度、两个时长的公开上限和 max_retry 的实现上限仍待确认，实施前必须补齐。此前建议的 128 字节、24 小时和 7 天未作为已确认规则。

字段名统一为 `execution_timeout_ms`。

平台先将省略的 execution_timeout_ms 规范化为 60 秒，再进行创建或幂等比较，保存最终有效值。

- 省略参数与显式传入 60000 等价。
- 显式传入 0、负数或非整数均非法。
- 不能把 0 当作未传。
- 输入解析时必须能够区分“未提供”和“显式提供 0”。

初版默认值固定为 60 秒，不随执行实例配置变化。平台时长上限属于统一部署配置，应在实现时公布并校验，不得低于默认值。

毫秒数转换为内部时长或时间戳时，需要检查溢出。后续改变默认值需要明确版本规则，不能破坏已有重试语义。

同一次逻辑提交的所有重试必须保持相同的最终配置，建议调用方首次提交就显式指定 execution_timeout_ms。

retry_delay_ms 在首次创建和幂等比较前规范化：

- 省略时使用 30 秒，省略与显式传入 30000 等价。
- 显式传入的值必须是大于或等于 15000 的整数毫秒；0、负数、小于 15000、非整数或超过平台上限均非法。
- 平台上限属于统一部署配置，不得低于默认值 30 秒。
- 将规范化后的值保存在任务详情 Hash，作为不可变初始配置。
- 与其他时长一样，毫秒转换为内部时长及时间相加必须检查溢出。
- ReportFailure、Reclaim 读取该保存值，用 Redis 当前时间生成重试到期时间，不由 Worker 临时覆盖。

初版采用平台范围内唯一的 task_id。两个不同 ID 可以提交内容完全相同的任务。

### 不允许由调用方指定的运行状态

以下内容由平台维护，不允许通过 Submit 指定：

- 当前状态。
- 当前尝试次数。
- 剩余尝试次数。
- 当前执行实例。
- 本次执行身份。
- 租约到期时间。
- 下次重试时间。
- 执行结果和错误。

`max_retry = 3` 表示最多允许首次尝试加三次重试，即最多四次执行尝试：

```text
max_attempts = max_retry + 1
```

授予执行权时计一次尝试。进程崩溃或领取响应丢失，也消耗已经授予的尝试次数。

Submit 本身不增加执行尝试次数。

提交请求的网络重试次数与任务执行的 max_retry 是两个不同概念，不能共用同一个计数。

### 单次执行超时的语义

- execution_timeout_ms 从 Server 启动本轮 handler 时开始计算，同时建立时长为 execution_timeout_ms 的本地定时器。
- 不从 Submit、Claim 请求发出、Redis 授予执行权或 Claim 响应返回时提前开始计时。
- pending、retry_wait、Claim 请求和响应的耗时，以及启动 handler 前的本地准备时间，都不计入单次执行时长。
- 每次重新领取并启动 handler 时，使用同一个不可变 timeout 配置，为新一轮提供完整的 execution_timeout_ms。
- 超时由 Server 本地定时器控制；续租不重置本地定时器。
- timeout 不是整个任务的总截止时间，也不是 Submit 或 Claim 网络请求的超时时间。

时间戳统一采用 Unix 毫秒，execution_timeout_ms、retry_delay_ms 使用整数毫秒。

不在 Redis 任务详情中设置 execution_deadline_at，也不在 Lua 中按执行时长强制拒绝操作。租约到期时间仅保存在 lease ZSET 的 score 中，不在任务详情中重复保存 lease_expires_at。重试到期时间 next_retry_at 仅作为 retry ZSET 的 score 保存，也不作为字段单独写入任务详情。

Server 从 Claim 响应中取得 execution_timeout_ms，完成本地登记后，在启动 handler 协程的同时建立时长为 execution_timeout_ms 的本地定时器及取消 context。handler 返回与定时器到期竞争，Server 只选择一个结果处理分支。不统计或扣除 Claim 耗时，也不需要比较 Server 与 Redis 的墙上时钟来计算执行超时。

本地定时器到期且 handler 尚未完成时：

1. Server 在本地将该轮结果裁定为超时，向 handler 发出 context 取消信号并停止续租。
2. 调用 ReportFailure 上报超时；超时裁定后，不再为该轮发起 complete。
3. handler 成功返回与超时处理之间必须在本地只选择一个结果处理分支。
4. ReportFailure 成功时释放 Redis 执行权，按尝试额度进入 retry_wait 或 failed；若已被 Cancel 或回收，前置条件不满足，不再修改。
5. 上报结果未知或重试耗尽时，停止续租，保留当前 Redis 状态由租约到期回收处理。此期间任务可能仍为 running，不能声称本地超时与 Redis 状态同时生效。

初版不承诺 Redis 严格按执行时长拒绝所有迟到成功；Server 暂停、网络延迟及已在途的上报可能造成超时处理延迟。不能把本地超时控制描述为存储端硬截止时间保证。

Go context 不会强制终止不配合的 goroutine，也不会撤销已经发生的业务副作用。

停止续租、发出取消信号或上报失败均不等于 handler 已退出。本地执行槽必须在 handler 实际退出后才归还，且只归还一次。

单次超时不退回已授予的尝试次数。ReportFailure 成功时按额度进入 retry_wait 或 failed；若 Cancel 已先进入 canceled，则拒绝超时上报并保持 canceled。上报失败不代表这些状态已经生效。

### 任务类型与 handler

task_type 是执行端 handler 注册表中的路由键。

同一个执行实例中，一个类型对应一个已注册处理入口；多个执行实例可以注册同一类型。

Submit 校验类型标识的格式。除非另行设计统一的类型注册信息，否则不能仅凭 Submit 成功就保证此时存在在线、匹配的执行实例。

调用方与执行端需要保证任务类型和业务参数格式一致。

## 3. 执行前置条件

- 输入参数通过校验，非法请求不能创建记录或入队。
- task_id 不存在时，允许创建新任务。
- task_id 已存在时，不再创建，按照第 8 节处理重复请求或内容冲突。
- 已有任务处于任何状态，都不能被重复 Submit 重置或重新入队。
- 当前执行身份和租约到期时间不作为新建 Submit 的输入；初版不设置取消标记。
- execution_timeout_ms 是允许提交的执行配置，Server 在成功领取后才据此控制本轮本地超时。
- 初版不提供整个任务的总到期时间参数。

## 4. 成功后的变化与返回值

### 首次创建

- 状态变化：无记录 → pending。
- 保存 task_id、task_type、原始 payload、max_retry、规范化后的 execution_timeout_ms、retry_delay_ms、queue = default 和 created_at到任务详情 Hash。
- 保存不可变的初始提交配置，供后续重复请求比较。
- 不要求另建一张表或复制一份初始配置，只要后续操作不覆盖原始值即可。
- 初始化 status = pending。
- 初始化 attempts = 0。
- 不初始化取消标记、execution_deadline_at 或详情中的 lease_expires_at，这些字段初版不使用。
- 初始没有执行身份、lease 或 retry 索引项、执行结果或执行错误。
- 将 task_id 加入当前逻辑队列的 pending 索引一次。

保存 timeout 配置不表示此时已经开始执行计时。

任务记录创建与入队的 Redis Lua 执行成功并收到确认后，才允许返回新建成功。该确认不等于任何持久化配置下都已落盘，不包含 MySQL 写入。

### 已有相同任务

- 返回原任务身份，表示提交目的已经达到。
- 不重新入队。
- 不重置状态、尝试次数、结果或创建时间。
- 原任务已经成功、失败或取消时，也不重新执行。

### 返回值

```go
type SubmitResult struct {
    TaskID  string
    Created bool // true：本次新建；false：已有任务且初始配置一致
}

// 服务端接口示意，不表示初版需要实现 SDK。
func Submit(
    ctx context.Context,
    req SubmitRequest,
) (*SubmitResult, error)
```

| 情况 | 返回结果 | error |
| --- | --- | --- |
| 新建成功 | 原任务 ID，Created=true | nil |
| 同 ID、同初始配置 | 原任务 ID，Created=false | nil |
| 同 ID、不同初始配置 | 无成功结果 | 可识别的 ID 内容冲突错误 |
| 参数非法 | 无成功结果 | 可识别的参数错误 |
| 提交结果无法确认 | 无确定结果 | 可识别的超时、连接错误或结果未知错误 |

error == nil 时返回非空结果。

成功结果不携带“任务一定仍在 pending”的承诺，因为执行端可能在响应返回前已经领取甚至完成任务。

## 5. 原子性与不变量

### 必须处于一致原子边界内的步骤

1. 检查 task_id 是否存在。
2. 不存在时，创建任务记录并加入 pending。
3. 已存在时，检查初始提交配置，返回已有任务或报告冲突，不修改已有任务。

不能依赖“先检查不存在，再分别创建和入队”的非原子流程。

初版使用 Redis Lua 支持并验证上述行为，不能仅因为采用 Lua 就默认已经满足。

使用 Redis Lua 时，需要在修改前校验输入、数据类型和业务条件。脚本隔离执行不等于运行时错误会自动回滚此前写入。发生部分写入后的自动检测、对账及修复不属于第一版功能；此类不一致不在正常原子执行保证内，不能假定回收器能够兜底。

### 不变量

- 在任务身份保留期内，同一个 task_id 最多对应一个任务。
- 首次提交不能留下只有任务记录或只有 pending 索引的半完成结果。
- 同 ID 的并发和重复提交不能额外增加 pending 项。
- 同 ID、不同初始配置不能覆盖已存在任务。
- Submit 不修改已存在任务的执行状态和运行数据。

“记录与 pending 同时存在”描述的是首次提交的原子结果。

在执行端正常领取之后，pending 中不再包含该 ID 属于合法行为。

## 6. 失败及结果未知时的行为

### 确定的请求错误

- 参数非法：返回参数错误，本请求不产生创建或入队效果。
- 同 ID、不同初始配置：返回 ID 内容冲突，不修改原任务。
- 原样重试上述错误通常无法解决问题，调用方应先修正请求。
- 不能擅自换新 ID 掩盖冲突。

### 存储或网络异常

连接中断、超时和存储访问错误，可能出现在操作生效之前，也可能出现在生效之后。

除非能够确定操作未执行，否则不能把错误解释成“任务肯定不存在”。

例如：

1. 平台向存储提交操作。
2. 存储已经创建记录并入队。
3. 存储确认响应丢失。
4. 平台向调用方返回错误。

此时任务仍然可能已经成功提交。

### 查询与安全重试

- 调用方可以通过 task_id 查询状态。
- 调用方也可以使用相同 task_id 和相同初始提交配置重新 Submit。
- 创建另一个任务时必须使用新 ID。
- 原操作已经生效时，重试返回已有任务。
- 原操作尚未生效时，某一次重试可以完成创建。
- 所有在途重复请求仍由原子创建与幂等规则处理。

是否自动重试由调用方决定，初版平台不实现客户端自动重试。

调用方若实现重试，应设置等待、次数或总时长上限，并响应自己的取消与截止时间。

重试耗尽仍可能结果未知。调用方应保留自己生成的 ID 和原始配置，用于后续查询或再次提交。

超时或连接错误不表示已确认提交失败，也不表示已确认成功。

存储或服务恢复之前，重试可能持续失败。调用方重试不能替代服务恢复，也不能找回存储已经丢失的数据。

## 7. 并发竞争规则

| 并发请求关系 | 规则 |
| --- | --- |
| 同 ID、同初始配置 | 首个成功创建者返回 Created=true；之后确认已有相同任务的请求返回 Created=false |
| 同 ID、不同初始配置 | 首个成功创建的配置成为该 ID 的提交配置，与其不一致的请求返回冲突 |
| 不同 ID、相同配置 | 视为两个独立任务，允许分别创建 |

发生网络故障时，成功创建者可能收不到成功响应。

因此，“只创建一次”不等于“调用方必定有一个请求观察到 Created=true”。

已有任务也可能被领取、完成或取消。重复 Submit 不能覆盖这些操作产生的变化。

将来增加清理时，清理与 Submit 的竞争规则需要与身份保留期共同定义。

## 8. 重复请求与幂等规则

### 识别方式

先通过 task_id 找到同一个逻辑任务，再比较初始提交配置，防止同一个 ID 被用于不同请求。

初版比较以下字段：

- task_type。
- 原始 payload。
- max_retry。
- 规范化后的 execution_timeout_ms。
- 规范化后的 retry_delay_ms。
- 固定的 queue（default）。

以下运行数据不参与比较：

- 当前状态。
- 当前尝试次数。
- 剩余尝试次数。
- 当前执行实例。
- 执行身份。
- 租约。
- 结果和错误。
- 运行时间戳。

execution_timeout_ms、retry_delay_ms 都是不可变初始配置；初版不保存 execution_deadline_at。

同一 ID 下仅修改 execution_timeout_ms 或 retry_delay_ms，也必须返回内容冲突，不能覆盖原配置。

第一版 Client 和 Server 只提交和处理 default 队列，不开放 queue 选项。queue 仍作为不可变字段保存并参与幂等比较；已有记录的 queue 不为 default 时返回冲突。

以后开放队列选择等提交参数时，应同步定义默认值、输入校验与比较规则。

### payload 比较规则

初版采用业务参数序列化后的字节比较。

空参数以同一种约定的空字节表示保存与提交。

相同逻辑提交的所有网络重试复用最初序列化的内容。

JSON 字段顺序、空白或其他编码差异可能导致冲突。

若以后需要按 JSON 值判等，再增加明确的规范化规则，本契约不隐含该能力。

### 有效保留期

初版在任务记录及初始提交配置保留期间提供幂等保证。

初版不由 Submit 自动删除或覆盖已有任务。

若未来清理任务记录且没有单独保留去重信息，清理后不再承诺识别相同 ID 的历史提交。

终态保留、手动删除和清理策略需要同时说明这一限制。

## 9. 崩溃与恢复行为

### 当前承诺的故障范围

在权威存储可用且数据完整的前提下，提交服务或执行进程崩溃，不能导致 Submit 留下任务记录与初始 pending 索引不一致的中间结果。

原子性与持久性是不同保证。

原子行为不能直接推导出存储进程崩溃、断电或磁盘损坏后仍然不丢数据。

### 各阶段行为

| 崩溃时机 | 应有行为 |
| --- | --- |
| 原子提交尚未生效 | 本次没有创建效果，调用方可以同 ID 重试 |
| 提交过程中 | 在 Redis 可用、数据完整且脚本正常完成的范围内，记录与入队原子生效；脚本运行时错误后的部分写入不自动回滚，初版不自动修复 |
| 已生效、响应前崩溃 | 任务保留，调用方可能结果未知，同 ID 重试返回已有任务 |
| 返回成功后提交服务崩溃 | 在约定故障范围内，任务不依赖该服务内存继续存在，恢复后仍可被处理 |

服务进程由进程管理机制或人工重新启动。

启动后读取现有存储，不清空任务、不重复重建 pending。

没有在线执行实例时，任务可以保持等待。

### 已确定的存储与待补充的部署边界

初版仅 Redis，不使用 MySQL，不存在 Redis 与 MySQL 双写或两者状态对账流程。任务查询以 Redis 为准。

Lua 正常执行成功并收到响应是运行时成功确认；Redis 的具体持久化及恢复配置仍需在部署时补充：

- 返回成功所依据的具体存储确认条件。
- 使用的持久化配置。
- 存储进程重启时可提供的恢复保证。
- 可能的数据丢失窗口。
- 验证范围以外的故障，例如永久磁盘损坏。

上述部署配置目前尚未定义。Lua 部分写入的不完整状态及自动修复也作为已知限制保留，初版不实现自动对账恢复。

不能将最终接口的成功承诺描述为无条件持久化，也不能在未说明边界时承诺任何故障下不丢任务。

## 10. 验收场景

提交原子性测试应先暂停 Worker 和记录清理逻辑，避免把正常领取导致的 pending 项消失误判成数据丢失。

| 场景 | 操作 | 期望结果 |
| --- | --- | --- |
| 首次合法提交 | 使用新 ID 提交合法请求 | 一条 pending 记录和一个 pending 项，返回 Created=true |
| 参数错误 | 提交空 ID、空类型、负数 max_retry、非法 timeout 或超出配置上限的参数 | 返回参数错误，不创建或入队 |
| timeout 默认值 | 省略 execution_timeout_ms 提交后，使用同 ID 显式传入 60000 | 保存有效值 60000，第二次返回已有任务，不冲突、不重复入队 |
| timeout 非法值 | 分别显式传入 0、负数、非整数或超过平台上限的值 | 参数错误，不创建、不入队 |
| retry_delay_ms 默认值 | 省略 retry_delay_ms 提交，再以同 ID 显式传入 30000 | 保存 30000 毫秒，第二次识别为相同配置 |
| retry_delay_ms 边界 | 分别传入 14999、15000、15001、0、负数、非整数和超过平台上限的值 | 15000 和 15001 合法；其余非法值不创建、不入队 |
| retry_delay_ms 冲突 | 先以 30 秒提交，再以同 ID 改为 45 秒 | 返回内容冲突，原配置保持 30 秒 |
| timeout 开始计时 | 保存 timeout 后让任务等待，并人为延迟 Claim 响应，再启动 handler | 等待和领取耗时均不计入超时；从启动 handler 时计满 execution_timeout_ms，不保存 Redis 执行截止字段 |
| 同 ID、同配置重复 | 连续提交相同请求 | 第一次新建，之后返回已有任务，不重复入队 |
| 同 ID、不同配置 | 分别改变 payload、task_type、max_retry、execution_timeout_ms 或 retry_delay_ms 再次提交 | 返回冲突，不修改已有记录 |
| 不同 ID、同配置 | 使用两个 ID 提交相同任务内容 | 创建两个独立任务 |
| 同 ID、同配置并发 | 无故障条件下并发提交 20 次 | 恰好一次 Created=true，其余 Created=false，只创建并入队一次 |
| 同 ID、不同配置并发 | 同时提交两个不同配置 | 一个配置创建成功，另一个冲突 |
| 已有任务运行或结束 | 任务被领取、重试或进入终态后再次提交原请求 | 返回已有任务，不重置运行数据、不重新入队 |
| 初始配置与运行计数分离 | 发生一次执行尝试后再次提交原请求 | 仍可识别相同初始配置，不因计数变化而冲突 |
| 创建完成但响应丢失 | 丢弃成功响应，使用原 ID 重试 | 返回已有任务，不创建第二个任务 |
| 存储已生效但确认丢失 | 丢弃存储确认响应，再以原 ID 重试 | 可能先结果未知，恢复后确认原任务存在，不重复入队 |
| 提交服务崩溃 | 在提交前后设置故障点，结束并重启提交进程 | 在约定故障范围内，记录和初始 pending 项同时存在或同时不存在 |
| 调用方安全重试 | 模拟持续断连，由调用方进行有界重试 | 可停止并保留原 ID 后续确认，不误报任务不存在 |
| 已确认提交后的服务重启 | 提交成功后重启服务，存储保持完整 | 任务仍存在且可继续被处理，不重复创建 |

网络故障测试中，应分别统计：

- 实际创建次数。
- 调用方观察到的返回结果。

不能要求故障下必定有调用方收到新建成功响应。

## 11. 实现约束与补充验收

依据 [ADR-0001](adr/0001-submit-client-and-storage.md) 和 [Submit实施计划](Submit实施计划.md)。

- Lua 新建分支在 HSET 前检查 pending 类型只能为 none 或 list；已有记录分支不要求 pending 存在或包含该 ID。
- 循环比较六项配置，任一字段缺失返回 incomplete，优先于 conflict；空字符串不等于字段缺失。incomplete 映射为可识别的存储数据异常，不返回成功、不补字段或重新入队。
- Redis 客户端由调用方配置和关闭，底层重试由调用方管理，平台不额外增加 Submit 重试循环；具体要求统一见 ADR-0001。底层重试可能在首次创建响应丢失后返回 Created=false。
- 补充验收：省略 max_retry 与显式 0 等价；timeout=1500ms 合法，retry delay=15001ms 合法；非整数毫秒拒绝；nil payload 与空切片等价；缺失 payload 返回 incomplete；queue 缺失返回 incomplete、不同返回 conflict；pending 错误类型不创建 Hash；nil 选项报错，零个选项合法。
