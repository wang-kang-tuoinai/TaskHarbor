# ADR-0007：Reclaim 的批次边界、检测范围与故障隔离

- 状态：已接受
- 日期：2026-11-09
- 关系：补充 ADR-0004、ADR-0006 的后台故障隔离设计；不改变 Renew 或结果上报的故障行为。修订 Reclaim 契约的 score 读取、批次校验和 pending 成员检测约定，不替代已有 ADR。

## 背景

Reclaim 需要将过期 running 按预算回收，并将到期 retry_wait 重新入队。无限处理积压会长时间占用 Redis；仅限制候选条数，却为每个候选扫描 pending List，仍会使成本随待执行队列增长。另一个选择是新增成员索引，但这要求多个操作共同维护新的不变量。

批量 Lua 也不提供错误回滚。逐任务检查后写入允许后续坏候选被发现时前面的任务已迁移；整批先验可以提供更明确的校验错误语义，但会让一个坏任务阻塞本批健康任务。回收故障还需要与既有执行、续租隔离，不能把停止恢复工作等同于取消所有 Handler。

## 决策

1. 租约回收与重试调度使用两个脚本，依次执行，各自原子选择、校验和迁移。每个脚本限量处理，不为完成全部积压连续补跑；两个脚本不构成整体事务。
2. 每个脚本先整批校验，再整批写入。可预见的校验异常保证当前脚本零写入；运行时故障不回滚，网络错误或非法响应仍表示结果未知，整体 error 也可能发生在第一阶段已成功之后。
3. 同一脚本的候选查询携带 score，检查合法性及到期，不为防并发额外重读。其他请求不能插入该脚本的查询与迁移之间。
4. 不扫描 pending List 查重，不新增辅助成员索引。依靠合法源状态、原子移除 retry 与入 pending 保证正常并发不重复迁移；明确放弃对 retry/pending 异常双重成员的主动检测保证。
5. 独立串行回收循环使用随机等待和独立请求预算，生命周期不绑定 Claim/Renew。暂时性网络错误不立即重试，下一轮重新选择候选；这是调度与压力控制选择，不是认定重复回收必然重复入队。
6. 第一阶段报错即结束本轮；一致性异常、明确不可恢复存储错误和非法响应停止本实例 Claim/Reclaim，沿用首个 Errors 通知机制。健康 Renew、Handler 和上报继续，不仅凭回收失败取消本地执行。
7. 租约回收的诊断原因固定为 lease expired，不推断 Handler 超时、崩溃或 Server 未正确上报；attempts 不变。调度数值、写入细则及验收场景统一见 Reclaim 契约。

## 后果与限制

- 一个坏候选会阻塞整批；第一阶段持续失败也阻塞第二阶段。坏数据可能使多个实例停止回收，不自动跳过、隔离或修复。
- 合法状态下的并发不重复入队保证，不覆盖人为破坏或部分写入产生的 retry/pending 双重成员；这种状态可能被追加重复项。
- 限批和抖动控制请求形态，但不保证脚本固定耗时、实例绝不同步或积压在固定时间内恢复。客户端超时不能中止已执行的 Lua。
- Errors 不是完整故障日志，也不表示全部后台工作退出；通知被抑制仍须执行对应故障处理。
- 保留健康续租和上报的机会。回收仍不强制结束旧 Handler，不能撤销业务副作用；普通回收不是存储损坏的对账修复机制。
- 本 ADR 是已确认设计，不表示回收功能已经实现或测试通过。

## 替代方案

- 单脚本处理两个阶段或无限清空积压：不采用，扩大单次执行范围，没有必要的跨阶段原子性需求。
- 逐任务校验后立即迁移：可行，但不采用；选择当前脚本校验失败零写入的明确边界，接受坏候选阻塞整批。
- 扫描 pending 查重：不采用，候选限量无法限制 List 全表检查成本；新增成员 Set 也暂不采用，避免扩大多个操作的索引维护范围。
- 回收故障停止全部续租、取消全部 Handler：不采用，故障不证明健康任务已经失权，会扩大影响范围。
- 两阶段独立调度或错误后立即重试：初版不采用，优先保持调度简单，接受第一阶段失败延迟重试调度及网络恢复后的等待。
