# ADR-0009：Cancel 的尽力通知与订阅生命周期

- 状态：已接受
- 日期：2026-11-17
- 关系：补充 Cancel 操作契约、ADR-0004 和 ADR-0008；细化 Start 在订阅网络等待期间与 Shutdown 的协调，不改变既有退出控制权和实际停止语义。

## 背景

Redis 中撤销执行权与本地 Handler 实际退出不是同一事件。可靠通知、执行登记握手可以缩小取消延迟和窗口，但需要额外状态与恢复协议。第一版选择 Pub/Sub，必须明确断线、早到、发布失败和消费退出的边界，不能以通知成功替代权威状态。

当前 Start 的本地启动可以短时间持锁完成；加入订阅确认后若保持同一锁等待网络，会阻塞 Shutdown。订阅资源还需要在正常排空期间继续工作，在真正退出前被关闭和回收。

## 决策

1. Client.Cancel(ctx, taskID) 返回结构化取消结果与错误。区分 canceled、not_found、already_terminal 及实际终态；透传调用方 context，不增加平台重试或修改共享客户端，明确底层重试可能改变最终结果分类。ContextTimeoutEnabled 的网络截止前提通过文档说明，不新增 NewClient 限制。
2. Lua 原子校验并取消任务，通知只是尽力加速本地停止。running 分支用原 owner 的频道和原 task_id/token 发布 JSON；写前完成编码，迁移后保护发布调用。仅发布失败不改变取消成功，由内部诊断与 slog 记录；不回滚、不重发、不新增公开通知成功字段。
3. 使用 PubSub.Channel()，连接恢复主要交给库，不自建可靠队列、确认或重放机制。通知渠道假定由可信平台组件使用；消费者不为每条正常消息再查 Redis。
4. 精确匹配执行尝试后复用本地撤销，停止续租资格、取消 Handler 和上报，不伪造失败且不提前释放槽。无记录或旧 token 忽略该条并继续；格式错误记录后丢弃。不缓存通知以解决登记前到达的窗口。
5. 订阅确认是领取前置条件。Start 短暂持锁进入 starting，锁外等待确认，再持锁复查退出状态后统一启动循环。失败清理并返回，对象不重启。Shutdown 覆盖启动中取消及迟到确认，不能等待没有生产者的后台 done。
6. 正常排空保留订阅，强制阶段或排空后的清理关闭自有 PubSub，实例完全停止前等待消费结束。非预期消息 channel 关闭停止 Claim/消费并通过既有 Errors 报告，其余健康工作继续；主动关闭不报错，不关闭调用方 Redis 客户端。
7. pending 写前检查成员存在，移除全部目标项而不专门检测重复数量；直接可查的 Set/ZSET 冲突写前拒绝，running/retry_wait 不额外扫描 pending。不扩大为通用数据修复。

## 后果与限制

- canceled 不保证 Handler 已停止或业务副作用被撤回。通知早于执行登记仍可能导致 Handler 启动，后续续租和上报由 Redis 拒绝。
- 断线遗漏不补发，消费积压可能丢消息；Channel 不提供每次接收错误，不能承诺所有订阅故障都通过 Errors 可见。channel 未关闭不证明连接健康。
- 发布失败与取消结果分离，保留权威取消事实但可能失去快速本地取消机会；重复 Cancel 不再次推送。
- Start 增加订阅网络等待，需扩展 starting 与 Shutdown 的协调。请求预算不承诺底层取消立即返回；不能提前声明实际 stopped。
- pending 取消成本随队列长度增长；不扫描其他分支的 pending 残留意味着有意限制损坏检测范围。
- 本文是已确认设计，不表示 Cancel 已实现或测试通过；具体预算、结果和验收以 Cancel 契约为准。

## 替代方案

- 通知必须确认送达才算取消成功：不采用，将权威状态与不可保证的本地退出混合。
- 发布失败让整个调用当作未取消：不采用，Lua 不回滚已经完成的迁移；仅发布错误采用内部诊断。
- 持久化通知、缓存早到消息或新增登记握手：初版不采用，接受明确窗口，避免扩大恢复协议。
- 自建底层接收、心跳和重连循环：不采用，优先复用库，接受错误可观测性限制。
- 在生命周期锁内等待订阅或未确认就启动 Claim：不采用，分别造成退出阻塞或主动留下未订阅窗口。
- 所有订阅故障取消全部 Handler：不采用，消息接收故障不证明所有执行已失权。
