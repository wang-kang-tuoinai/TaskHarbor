# 多进程故障恢复演练方案

- 状态：测试设施已实施，2026-11-14 完成五个场景的多进程验收，结果见第 11 节。
- 确认日期：2026-11-14。
- 目的：验证 Submit、Claim、Renew、complete、ReportFailure、Reclaim 在真实 Redis 和多个独立进程中的协作与故障恢复。不是极限吞吐量测试，不以 1000 个任务推导容量保证。

## 1. 依据与边界

遵循 [领域术语](../GLOSSARY.md)、[Claim 契约](Claim操作契约.md)、[Renew 契约](Renew操作契约.md)、[complete 契约](complete操作契约.md)、[ReportFailure 契约](ReportFailure操作契约.md)、[Reclaim 契约](Reclaim操作契约.md)及其关联 ADR。

本方案不改变平台业务行为，不新增生产依赖或公开 API。独立演练入口、故障控制和验收工具属于测试设施。查询、Cancel、公开 Shutdown、Redis 持久化恢复、主从切换及自动修复不在范围内；不为演练提前实现它们。本次没有新的架构取舍需要 ADR，也不新增领域术语。

## 2. 环境与部署

- 使用 Docker 启动专用测试 Redis，不连接已有业务实例。每个场景独立数据集和运行标识，场景之间清理须在证据保存后进行，不能在消费期间清空或手工修复平台索引。
- 运行 3 个独立 Worker 进程，每进程包含一个 Server，并发设为 10，总 Handler 并发最多 30。1000 是每个场景累计提交量，不是同时执行量。
- 独立提交器使用真实 Client.Submit；观察器通过只读 Redis 查询验收，不要求先开发查询 API。网络故障只影响目标 Worker 到 Redis 的路径，不影响观察器、提交器和其他 Worker。
- 演练期间不自动重启被杀 Worker；其他两个进程继续消费与回收。场景结束后统一清理进程，不将强制进程清理称为优雅退出。
- Redis 客户端遵循现有 Server 前置条件：MaxRetries=-1、ContextTimeoutEnabled=true；记录实际 I/O 超时等配置，不修改平台重试语义。

### 环境准备核验

方案确认前的只读核对发现 Docker CLI 已安装，但当时无法连接 Docker Linux 引擎；该历史检查不足以证明环境可用。实施时已重新验证引擎和端口，并新增独立 Worker 测试入口；实际环境及命令见第 10 节。既有集成测试仍自行启动本机 Redis。

实施准备时需要验证并记录：

1. Docker 引擎可用、测试网络和端口可达。
2. 选定并固定 Redis 镜像版本，记录实际版本或镜像摘要，先做连接与脚本兼容性检查；不使用浮动版本掩盖环境变化。本轮固定的镜像见第 10 节。
3. 选定测试专用可控网络代理并验证隔离效果，包括既有连接和重连路径不能绕过代理。本轮采用测试专用 RESP2 TCP 代理。
4. 区分关闭连接产生快速错误与保留连接造成超时两种故障机制，报告实际采用的机制，不把所有断网效果混称为丢包。

本轮不重启 Redis 或验证持久化；不得将无持久化 Redis 重启后的丢数据解释为平台恢复缺陷。现有版本的集成测试记录不代表新 Docker 镜像已验证。

## 3. 任务与参数

| 项目 | 确认值 |
| --- | --- |
| 每场景任务数 | 1000 |
| Worker 进程数 / 每进程并发 | 3 / 10 |
| 租约 | 30 秒 |
| 续租间隔 | 6 秒 |
| 回收间隔 | 10 秒，保留平台已有抖动 |
| 执行超时 | 60 秒 |
| 重试等待 | 15 秒 |
| max_retry | 10，即最多 11 次执行尝试 |
| 总截止 | 从开始提交起 10 分钟 |

每场景生成唯一运行标识和 1000 个确定 task ID，保存预期清单、提交参数和正确结果。900 个任务模拟工作 1 秒，100 个模拟工作 20 秒，按固定规则交错提交。长任务用于覆盖续租和故障窗口，不依赖任务全部瞬间执行完。

通过 Submit 创建任务，不直接向 Redis 写初始任务数据。提交网络错误时使用同一 ID、相同参数重新确认，禁止换 ID 补交导致实际任务数增加。记录提交确认数量及未确认项；提交未确认也消耗总时间预算，不能静默排除这些任务。

Handler 使用可预测的纯计算结果，例如根据输入数值计算平方，通过 SetResult 保存后返回。模拟等待响应 context 取消，记录开始、返回及取消等事件；不发送真实邮件、扣款或修改业务系统。测试不承诺业务副作用恰好发生一次。

主动失败场景固定选择 100 个任务，在 Task.Attempts ≤ 2 时返回错误，之后正常执行。规则依赖 payload 和平台提供的 attempts，不依赖进程内计数。Claim 已生效但响应丢失也消耗 attempts，因此此规则表示前两次执行尝试，不保证必定观察到两次 Handler 错误返回。

## 4. 场景与触发

每个场景使用独立的一批 1000 个任务，先运行无故障基线，再分别运行故障场景，不同时叠加主要故障因素。

| 场景 | 操作 | 主要证据 |
| --- | --- | --- |
| 无故障基线 | 不注入故障，普通 Handler 正常执行 | 全部结果正确，attempts 均为 1，无无故重试 |
| Worker 宕机 | 目标 Worker 至少启动一个长任务后，强制结束该进程 | 已在执行的任务失去原执行实例，其他实例回收并重新领取，最终完成 |
| 短暂断网 | 目标 Worker 启动长任务后，隔离其 Redis 路径约 5 秒再恢复 | 隔离确实发生，记录网络错误与恢复后的推进，结合实际租约判断重试 |
| 跨租约断网 | 同样触发，隔离约 45 秒再恢复 | 至少一个目标执行尝试确实租约到期，并被回收或重新领取；检查旧身份不能覆盖新结果 |
| 主动失败后恢复 | 固定 100 个任务按前两次尝试失败规则执行 | ReportFailure → retry_wait → pending → Claim → completed 链路 |

故障按实际 Handler 启动事件触发，不只在启动后固定 sleep。记录目标进程、任务 ID、attempts、故障开始与结束时间；观察器可记录当时的 Redis 状态与执行身份作为关联证据。

短暂断网也可能发生在剩余租约不足的时刻，因此不要求该场景绝不重试。跨租约断网不能仅以“隔离持续 45 秒”判定覆盖成功，必须有到期和回收证据。若未命中目标行为，即使任务全部完成，也不能宣称该故障场景通过。

旧身份不能覆盖新结果需要有有效观测或针对性的验证证据。若本次运行没有产生迟到上报，不得仅凭最终 completed 声称已实际覆盖这场竞争；应在报告中注明覆盖不足，实施时补足测试控制，不擅自修改平台执行行为。

## 5. 观测与错误处理

### attempts 与 Handler 启动记录

attempts 是 Redis 成功授予执行权的次数，不等于业务函数启动次数。领取响应丢失后可能 attempts=2 而只观察到一次 Handler 启动；执行中被杀并恢复后则可能二者均为 2。

记录二者用于区分恢复路径、发现“重试很多次后才完成”掩盖的问题，不要求它们总相等。强杀可能丢失尚未保存的启动日志，观察到的启动次数只是辅助证据，不为精确统计另建持久化协议。attempts 以 Redis 为准，日志缺失不证明 Handler 没启动。

记录每个进程的标识、任务 ID、attempts、事件时间和故障时间线；保存 attempts 分布、最大值和日志可观察启动次数。不用 Errors 沉默代替健康判断。

### Errors 的使用

演练 Worker 持续接收并记录 Errors，收到通知不自动退出。Errors 只通知首个导致停止领取的后台致命错误，不表示所有协程已经退出；直接退出会扩大原本保留健康续租和上报的故障范围。

本方案预期可恢复的场景中，出现非预期致命错误就判定失败并分析，即使最终其他实例完成了全部任务也不能忽略。进程只在明确故障注入或场景清理时按演练控制结束。

## 6. 验收标准

每个场景均满足以下要求才可通过：

1. 预期清单中的 1000 个任务全部存在，并在总截止前进入 completed；不以 Redis 全库记录数量代替逐 ID 核对。
2. 每个 result 与预期计算结果一致，不仅检查状态。
3. 收敛后，这批任务不残留于 pending、active、lease、retry，也不保留 owner_id、attempt_token。
4. 无故障基线所有任务 attempts=1；故障场景 attempts 不超过 11，记录分布并分析异常反复重试，不能只看最终成功。
5. 故障场景具有实际命中及恢复证据；旧执行尝试不得覆盖新一轮状态或结果。重复执行本身不直接判错，平台不保证业务恰好执行一次。
6. 没有非预期致命错误；平台状态没有因演练工具自动退出或手工修复而被掩盖。
7. 10 分钟截止不自动延长，不现场增大重试额度直到成功。到期未完成、额度耗尽或结果错误均记录为失败，保留现场后分析。

运行中分次读取 Hash 与索引可能跨越迁移时刻，不能把这种监控采样直接判为数据不一致。严格一致性检查使用一致快照或在收敛后进行；观察器不能修改租约、状态和索引帮助任务完成。

## 7. 实施与执行顺序

1. 准备专用 Docker Redis、可控代理及环境检查，固定版本并记录配置。
2. 增加演练专用提交、Worker、观察验收和故障控制入口，复用平台公开能力，不重构业务模块。测试工具内部组织形式由实施时按简洁性选择。
3. 实现预期清单、结构化事件记录、截止控制、证据导出和进程清理；先验证提交数量、故障路径及验收工具自身有效。
4. 运行无故障基线，通过后分别运行四种故障/失败场景。每场景使用新数据集，故障只作用于明确目标。
5. 保存报告与现场证据后再清理。失败时先导出状态和日志，不提前删数据、不以重跑覆盖原失败记录。
6. 汇总实际结果及未覆盖项，再按项目文档规范更新进度。现有单元和集成测试仍保留，本演练不替代它们。

## 9. 已知限制

有限重试只提供有限恢复机会，不能保证永久故障下完成。必须最终解除网络故障并保留健康消费者和回收循环。

1000 个任务和 30 个并发不构成生产容量结论；本方案也不验证 Redis 数据丢失、复制或持久化恢复。观察日志不是完整执行审计，最终 completed 也不能证明每个任务只执行过一次。

本文前九节约束演练行为，测试设施、实际环境和执行结论分别见后续章节。

## 10. 测试设施与运行方法

演练设施位于 `tests/recovery/`，全部使用新增的 `_test.go` 文件。Worker 由测试二进制启动为三个独立子进程，通过公开 Client、Server 和 Handler 接口调用平台。既有生产源码和测试无需修改。

本机选定的镜像为 Redis 7.4.9、Linux/amd64，固定摘要如下。测试使用 `--pull=never`，执行前须保证该摘要的镜像已在本地缓存，并能访问 Docker Linux 引擎。

```text
redis@sha256:b2b95679e3b46fb51864949ed25ea976fc3a6bcc00a40a1bc00d568cb2822e50
```

在仓库根目录执行完整演练。每场景仍采用本方案的 1000 个任务及原定时间参数。

```powershell
go test -tags recovery -race ./tests/recovery -run '^TestMultiProcessRecovery$' -count=1 -timeout 60m -v
```

同时执行既有 Redis/TCP 集成测试时使用以下命令。既有集成夹具仍需要 PATH 中的本机 `redis-server` 或 `TASKQ_REDIS_SERVER`。

```powershell
go test -tags integration,recovery -race ./... -count=1 -timeout 60m
```

测试专用 RESP2 TCP 代理只作用于 Worker 0。短暂断网关闭其既有连接，并使重连请求快速失败。跨租约场景在长任务启动后布置结果请求屏障，由该轮真实 complete 请求触发 45 秒黑洞隔离，保留客户端连接以触发 socket 超时。请求原始字节被保存，待新一轮完成后再交付 Redis，要求返回明确拒绝，并比较交付前后的完整任务 Hash。

每场景创建专用 Redis 容器，使用 `EVAL_RO` 一致快照读取验收数据。环境、镜像摘要、测试源码校验值、预期清单、逐进程日志、故障时间线、最终状态及报告保存在 `.scratch/recovery/<运行标识>/`。报告通过前逐 ID 校验 1000 个结果、attempts、当前身份及四类索引。

子进程日志排空后还会检查 stderr 中的 race 警告，发现警告即判定失败，避免强制进程清理掩盖 race 检测器的最终退出码。

证据导出完成后强制清理 Worker 和容器。若最终状态快照读取或写文件失败，仍清理 Worker 和代理，但保留 Redis 容器及专用 Docker 网络，并在 `report.json` 中记录资源标识，供后续诊断。演练的原始证据保留在本地，不随 Git 提交。
